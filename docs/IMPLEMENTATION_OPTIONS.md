# Варианты дальнейшей реализации

## Вариант A: Google Sheets → Web Dashboard

Оценка: 2–4 недели до production-версии после согласования PoC.

Состав работ: read-only Google Sheets API/service account, устойчивый mapping листов, валидация и журнал ошибок, кэширование, авторизация руководителей, автоматическое обновление, deployment и мониторинг.

Плюсы: менеджеры сохраняют привычный ввод; минимальные организационные изменения; быстрый запуск; таблица остается доступным резервным интерфейсом.

Минусы: хрупкая позиционная структура листов; ошибки формул и ручного формата попадают в источник; сложно обеспечить строгую валидацию, историю изменений и роли; API-квоты и задержка обновления.

Рекомендация: оптимальный следующий этап. Сначала стабилизировать read-only mapping и добавить скрытый технический справочник структуры в отдельной копии книги либо конфигурации web-приложения, не меняя текущий файл без согласования.

## Вариант B: Полноценное Web Application

Оценка: 8–14 недель для первой production-версии; точнее после описания ролей, процесса согласования и интеграций.

Состав работ: БД, авторизация и роли, интерфейс ежедневного ввода, планы, справочники, валидация, расчет KPI/премий, audit log, импорт истории, уведомления, отчеты, резервное копирование и администрирование.

Плюсы: единая модель данных; строгая валидация; надежные формулы; история и ответственность изменений; удобные роли, workflow и масштабирование аналитики.

Минусы: больше стоимость и срок; миграция истории; обучение менеджеров; требуется владелец бизнес-правил и приемка расчетов; выше требования к поддержке.

## Предлагаемый путь

1. Утвердить PoC и состав ключевых экранов.
2. Реализовать вариант A, параллельно нормализуя модель данных за API-слоем.
3. Накопить 1–2 месяца обратной связи и описать правила ввода/согласования.
4. При подтвержденной ценности перенести ввод в web поэтапно, сохранив экспорт в Sheets на переходный период.
